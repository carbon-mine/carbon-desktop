# Protected Windows instance state

`carbon_session::windows_state` prepares writable player data for the trusted launch host on Windows x64 with local NTFS. The caller must resolve an existing Carbon instance UUID and its application-owned library before acquiring a lease. The state root is `instances-v1/<instance>/protected-state-v1`. It starts empty, separately from any authored world or existing `game` directory. The host keeps the lease and journal in the sibling `.protected-state-host-v1` directory.

This primitive is unwired. Production protected Play remains unavailable.

## Launch and recovery contract

1. Acquire `StateLease::acquire(library_root, instance)` under the trusted launch coordinator's admission rules. A file lock serializes state changes for the instance. Call `unfinished_run()` to identify a prior run. When no native boundary could have started, `recover_unarmed()` can reconcile the recorded grants.
2. Allocate a fresh, random run UUID and call `prepare(run)`. Use `profile_name(instance, run)` when registering the exact run's AppContainer. The state path is available only after Carbon has recorded and verified all grants and marked the journal armed. Configure the eventual launch to keep verified JDK, code and native library paths separate from this writable directory.
3. Keep the lease until the supervisor has verified that the exact run's native process boundary is empty. Call `retire_after_drain(run)` only after obtaining that proof. Reacquiring the file lock after a crash does not establish drain. Arm state survives host restart. If the launcher fails before starting a process, it must still establish that no process entered the boundary before explicitly retiring the grant.

Carbon creates the new state directory with an inheritable low-integrity label. It preserves existing owner, group, integrity and unrelated DACL entries. It refuses to prepare a tree that already contains application-package or capability allow entries. A fresh run receives directory traversal and read/write access, and read/write/delete access to files. The grant adds no file execution, permission editing, or ownership rights. Runtime and profile registration, native process ownership and launch restrictions remain the caller's responsibility. [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) · [ACE inheritance](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules)

The journal binds the run and derived SID to the state directory and each recorded object's NTFS volume and file ID. Carbon flushes the bounded record before publishing it and changing ACLs. Recovery checks journaled ACLs against their exact before and after fingerprints and removes only the run's known entries. For files or directories created during the run, it checks the shape and inheritance of the entries before stripping them. Security writes use open handles. The fingerprint read and `SetSecurityInfo` call are separate operations. ACL writers must cooperate under the instance lease, since another writer can change the DACL between the fingerprint read and the write. [File identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) · [SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo)

## Limits and verification

Recovery refuses missing, renamed or replaced journaled objects, reparse points, hard links, unsupported ACLs and unexpected changes. A successful atomic replacement preserves the new save, but the replacement does not establish whether the original identity was deleted or moved outside the inspected tree. Recovery retains the journal and blocks a new grant in that case. Directory traversal is bounded to 1,024 objects and 16 levels. An interruption between initial directory creation and enrollment can leave an unmarked directory that requires trusted operator review. Recovery keeps player bytes, conflicting permissions and the journal available for review. Concurrent privileged edits and power-loss behavior remain outside the exercised evidence.

Run `cargo test --locked -p carbon-session windows_state` on Windows x64. The tests use disposable directories and the host token. They cover serialized leases, per-run and per-instance SID separation, native ACL inheritance and retirement, preserved world/settings canaries, journal identity substitution, conflicting ACLs, interruption before enrollment and interrupted grant recovery. The atomic replacement test runs a second lease after a clean first save, verifies that replacement changes the NTFS identity, then confirms that cleanup and relaunch are refused after restarting the lease, with the new save, outside canary and DACLs intact.

For the separate headless AppContainer test, run:

```powershell
cargo test --locked -p carbon-session windows::sandbox::state_worker::appcontainer_writes_and_reopens_only_scoped_player_state -- --ignored --exact
```

An ordinary non-elevated Windows x64 run verified two different AppContainer SIDs with zero capabilities before resuming a fixed test executable in a one-process job. The first worker updated existing state and created a file. The second read the created file and updated the same state after the first lease retired. After each retirement, the same AppContainer profile ran the executable again and was denied read and write access to both formerly writable files. During the active lease, both profiles were denied read and write access to the adjacent `game` directory canary and the separate instance's protected-state canary. They were denied read access to the host journal and write access to a staged read-only runtime canary. The host verified all canaries remained intact. The test registers and removes disposable AppContainer profiles and uses temporary fixture data. Safe retirement after an atomic save replacement and qualification of actual game launch still require work. The existing windowed Java fixture remains separate.
