# Accounts and entitlements

## Review fixtures

`carbon-account` evaluates synthetic entitlement transitions in memory for the review fixtures. Its public production-facing `fixture_play_blocker()` explains why the current shell cannot start a live game. The fixture adapter has two enum identities (Forest and Coast), typed provider observations and synthetic integer timestamps. It has no credential fields, HTTP client, browser, storage backend, launch permission or dependency on a Carbon service.

| Exercise | Expected evidence |
| --- | --- |
| Start without an approved application registration | A missing registration blocks observations and both play modes. A synthetic registration exercises only the adapter. |
| Select Forest, record a current grant and switch to Coast | Coast starts with unknown entitlement. A negative for Coast applies only to Coast. Switching back restores Forest's observation. |
| Sign out | The selected identity and its observation are removed. Signing out a different identity preserves selection. Selecting a signed-out identity requires a new observation. |
| Disconnect the fixture provider | Online checks report an unavailable provider. An attempted refresh during an outage preserves the last observation. Offline requires an explicitly selected offline mode, a complete fixture install and a current offline grant for the selected identity. |
| Expire, replace or revoke an observation | The upper validity bound is exclusive. A fresh definitive negative supersedes a prior grant for both modes. Stale or inconsistent timestamps are refused. The adapter records the greatest observed time over its in-memory lifetime so changing identities or moving the clock backwards after expiry cannot revive a grant. |
| Complete all synthetic eligibility checks | The result is `SyntheticEvidenceOnly`. A real game launch remains blocked. |

Run `cargo test --locked -p carbon-account` from the Desktop checkout. Tests drive selection, sign-out, verified observations, expiry, clock reversal after expiry, offline input requirements, provider unavailability and denial of actual play. Desktop tests also cover compiled client precedence, non-nil local client validation, public-ID-only persistence and clearing, a root with no configuration, and vault namespace separation after a client change. The test timestamps and eligibility rules are fixture inputs. The fixture stores no grants across app restarts.

## Microsoft consumer accounts

The app needs its own Microsoft public-client application registered for personal Microsoft accounts, with public client flows enabled, and its own Minecraft Game Service Access approval. A client ID is public application configuration. The core uses the Microsoft consumers device authorization flow with the `XboxLive.signin offline_access` scopes. The shell displays the short user code and opens the validated Microsoft device-login page when the user chooses to proceed. The password and consent interaction take place in the system browser. [Microsoft device authorization documentation](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code) · [Minecraft Game Service Access review](https://aka.ms/mce-reviewappid)

After authorization, the core exchanges Microsoft access for an Xbox User token, then an XSTS token for the Minecraft relying party. The Minecraft exchange uses the single-user hash from the XSTS reply for that token. The core exchanges XSTS for Minecraft access and requests the Java entitlement list and profile from Minecraft Services. A recognized `game_minecraft` or `product_minecraft` item and a valid Java profile must both be present to publish the UUID and name. This is an online check against the authenticated service responses. If the endpoint does not report the expected Java entitlement, the core leaves sign-in unverified. [Xbox user hash and XSTS tokens](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/service-authentication/security-tokens/live-security-tokens) · [Xbox website authentication](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/fundamentals/s2s-auth-calls/service-authentication/live-website-authentication) · [Horizon account documentation and endpoint evidence](https://github.com/horizon-rust/horizon/blob/main/docs/microsoft-account.md)

Run the blocking client on a worker. Keep the opaque device authorization in Rust and call `poll` when its returned delay has elapsed. The core applies the advertised minimum interval, `slow_down`, throttling delays and bounded connection backoff with a monotonic expiry. Cancellation takes effect before or after a network request and between exchanges. In-flight requests can take up to 12 seconds. The provider URLs are fixed, HTTPS uses platform certificate verification, redirects are refused, and the transport limits response size. Error messages use fixed application text. [OAuth device authorization grant](https://www.rfc-editor.org/rfc/rfc8628)

The shell owns credential storage and account lifecycle. The core returns a Rust-only refresh token for OS credential storage when the provider granted one. Refresh rechecks ownership and profile, returning a rotated token when supplied and retaining the previous token when omitted. `RefreshRejected` means Microsoft returned HTTP 400 with `invalid_grant`. Transient, registration, entitlement and profile failures have distinct outcomes. The online verification describes the profile at check time, with its lifetime bounded by the Minecraft access token. The core does not expose a game bearer or issue offline play grants.

The locked crate tests use scripted transport responses, a fake clock and locally constructed HTTP requests. An end-to-end browser and Java entitlement check requires Carbon's approved registration and an entitled account.

## Desktop account service

The shared desktop account service accepts a compile-time `CARBON_MICROSOFT_CLIENT_ID`. A valid compiled ID always wins. Without one, an operator can opt in per install by entering a public client ID in the native account window. That action requires a UUID, a non-zero value and explicit confirmation that the operator controls the ID and that Minecraft approved it for sign-in from this deployment. The value is a public application ID, not a secret or token.

Only the public ID is stored, in the small atomic app-owned `account-client.json` setting under the account root. It is restored on the next process start. The running worker keeps its original registration until restart, so changing or clearing the setting never swaps a live vault namespace. Clearing the setting does not delete profiles, saves, account metadata or OS credential entries. A different client ID has a different vault namespace and cannot read credentials saved under the previous ID. Session-only and explicit test or fixture registrations do not read the local setting.

Unconfigured builds show the account feature as unavailable with a neutral explanation and an external **Get Minecraft Launcher** action that opens only `https://www.minecraft.net/en-us/download`. The native account window displays the short-lived user code, status and verified profile name. The service handles device polling in a blocking worker, removes a cancelled or expired challenge and opens only the validated Microsoft device-login URL on explicit request. Provider rejection messages refer to the configured client and configuration help; runtime copy does not describe an application-review backlog or development timing.

The service supports up to 16 profiles. A separate OS vault slot protects each refresh credential, scoped to the app root, application ID and Minecraft profile UUID. The app root stores the profile UUIDs, their public names and the selected UUID. A lock serializes metadata and vault changes across editions. Windows uses Credential Manager and Linux uses an encrypted desktop Secret Service connection through the session bus. A macOS Keychain backend is available in the crate. A Linux session without Secret Service, a denied or locked vault, or a credential that exceeds the native store's limit can still use interactive sign-in for the current session. Only profiles with a successfully saved credential can be verified automatically on restart.

The active profile is restored and checked online on startup. Other saved profiles are listed and become verified when selected or refreshed. Switching uses a still-current verification in the same process, when available. Refresh checks the requested UUID matches the account returned by Minecraft before rotating the corresponding credential. Revocation removes that profile's matching credential. A transient or entitlement error leaves other accounts and the targeted saved credential available for recovery. Sign-out is scoped to the selected profile, removes its vault entry before confirming success and preserves instance data. A failed vault deletion can be retried explicitly for that account.

The native vault smoke test uses a temporary app root and an isolated synthetic credential. Run it from an interactive desktop session with its credential store available using `cargo test --locked -p carbon-account native_vault_compare_replace_and_remove -- --ignored`.

See [Play authorization](play-authorization.md) for the native admission contract and the remaining provider-policy and gameplay prerequisites.

## Svelte/Tauri account window

The toolbar opens an owned Win32 dialog on Windows and a modal GTK dialog on Linux. Choose a saved account to switch to it, refresh the selected active account, or confirm sign-out for that account. The dialog also handles adding an account, copying the short user code, opening the browser and cancelling a pending operation. A failed credential deletion offers retry for that account. Closing the dialog cancels work started in it when the service can still cancel. The toolbar opens account information without advertising a sign-in action in unconfigured builds. Play requirements show active-account verification explicitly. The status updates when the native dialog closes. macOS currently reports that the Tauri native account window is unavailable.

Both shells use `carbon_account::desktop::Accounts`. Tauri gives it the same app root as its library, so GPUI, Tauri and disposable review runs have separate registries and vault slots. The bundled main WebView can call `minecraft_account_status` for a redacted availability or verification enum and `show_minecraft_accounts` to open the modal dialog. The native dialog keeps account names, UUIDs and device codes out of that interface. Account verification and protected game launch are separate; Play opens requirements and synthetic instances still refuse execution.

Build the frontend with `bun run build` before running `cargo test --locked -p carbon-desktop -p carbon-account`. For a credential-free check, build with no Carbon application ID and run the Tauri executable with `--temporary-review --sample-vanilla --seed-review`. Open **Minecraft account** on the toolbar. From a personal instance, open **Play** and check that its requirements direct you to the native account window for the reason sign-in is unavailable. The owned dialog shows neutral sign-in and setup copy. Check Tab, Escape, focus return, the platform's assistive technology and light and dark themes on the desktop you are qualifying. Live sign-in and Java Edition entitlement require the configured registration and an entitled account.

For renderer coverage, build `dist/` and run `python scripts/check-tauri-account-renderer.py` with Playwright and an installed Chromium browser. The fixture checks the toolbar label, native-dialog request, keyboard focus after close, and Play requirements for unconfigured, unsupported, ready-to-sign-in and verified states.
