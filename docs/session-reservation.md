# Protected sample run reservation

The fixed Windows x64 Java sample holds its existing exclusive per-instance `sample.lock` from reservation through any save publication and transient cleanup. A separate instance can hold its own lock. The managed runtime remains read-locked during its trusted copy into the sample's private stage. The transient registry's short lock covers ownership records and cleanup, then releases before process creation or waits.

Each reservation generates a fresh UUID. The transient ownership record pairs the run UUID with the exact instance UUID. Before the host asks Windows to create the suspended process, it flushes and atomically publishes a no-replace `pending-run-v2` record in that instance's sample-only directory. The record carries the run UUID and originating Windows session; it holds no executable, account credential, or PID.

The protected run creates a named job object, `Local\CarbonDesktop.Sample.Job.<run UUID, no hyphens>`, with kill-on-last-close and a one-process limit. Its DACL grants the launcher's user only `JOB_OBJECT_QUERY`; the creating handle keeps full control, so another process cannot reconfigure or terminate the tree through a fresh open. A launcher that refuses an existing name never adopts someone else's job. On admission, a `pending-run-v2` record left by a lost owner is retired only when the record's session matches the current Windows session and that exact named job is absent or reports zero active members. A live job, another session, an unreadable job or an observation error returns the recovery-required error. Legacy `pending-run-v1` and damaged records also stay fenced.

If creation fails before Windows returns a process, the host can clear its own record. Once a process has been created, the record can be cleared after live job accounting reports zero active members. If admission validation rejects the suspended root, the host also waits on that exact process handle. Error paths attempt bounded termination and drain. A verified forced drain allows the record to clear but returns the original sample error instead of publishing a count.

An owner disappearing or losing the ability to observe the boundary leaves the record in place. The next launch in the same session verifies the named job before admitting anything. Clearing a record requires matching the current UUID through a Windows handle validated as a regular file with one link and no reparse point. The code never signals a process by a number read from storage.

The named job is scoped to its Windows session (a `Local\` name), which is why a record from another session stays fenced instead of being read as drained. Another process running as the same user can pre-create the job name and force a refusal, or open a query handle that keeps a live job observable; both fail closed. It cannot reconfigure, terminate or forge drain evidence through a fresh open. Restricting the job further, or a cross-session witness, remains a separate hardening decision.

Older v1 ownership records have no instance UUID. A recognized v1 record with a free or unreadable owner lock blocks new protected samples because the old run cannot be associated with a specific instance. A live v1 owner still holds its own sample lock. Live v1 and v2 owners can coexist with unrelated new runs. Recovery preserves legacy and unrecognized records and does not remove unrelated files.

`cargo test --locked -p carbon-session` covers two real test processes contending for one instance while the other instance remains available. The child reports a distinctive status and a deliberately misspelled test filter cannot satisfy it. The tests also cover an owner exiting without running destructors, restart recovery only after the named job is absent in the recorded session, a live named job still fencing its instance, a record from another session staying fenced, a refused duplicate job name, a denied control open, migration from a live to an unresolved v1 owner, retained transient data until verified drain, preservation of unrecognized records, and refusal to clear a mismatched or hard-linked run record. A real fixture window exits on the delivered close request, a window that ignores the request survives until the close bound and is then terminated, and the production stop leaves a windowless tree alive before its bound expires.

This is a protected-sample reservation only. It provides restart recovery for a lost owner whose `pending-run-v2` record can be verified against its named job. A live run is also listed in an in-process directory keyed by its run UUID: `active_runs` and `inspect` return only the run UUID, instance UUID and a redacted phase, and `stop` targets that run's own job. `stop` first asks every visible top-level window owned by a member of the job to close, which lets a game turn the request into its own save and exit. The request is repeated while the tree is alive, so it still reaches a window that appears after the stop was accepted. A tree that is still alive after the documented five-second close bound is terminated. The owner performs the only drain observation and record cleanup, so a forced stop never publishes the disposable sample save. Stopping run A cannot affect a later run B or another instance, a repeated stop while draining reports the same phase and starts no new bound, and an unknown or already retired ID changes nothing. The owner claims the empty tree as `finishing` the moment it observes drain, so a stop request that arrives afterwards reports `finishing` and cannot replace the completed outcome; a stop that claims the run first returns the stopped error and does not publish the disposable sample save. The directory exists only inside the process that owns the run, so neither shell wires it yet and another process cannot stop a run through it; the named job's DACL still refuses control opens from elsewhere. It does not offer a force-unlock operation on legacy or unrecognized records, a production game runner, or cross-process stop. Unknown outcomes remain fenced until an OS boundary can be verified. Player saves and installed instances remain outside this fixture storage.
