# Protected sample run reservation

The fixed Windows x64 Java sample holds its existing exclusive per-instance `sample.lock` from reservation through any save publication and transient cleanup. A separate instance can hold its own lock. The managed runtime remains read-locked during its trusted copy into the sample's private stage. The transient registry's short lock covers ownership records and cleanup, then releases before process creation or waits.

Each reservation generates a fresh UUID. The transient ownership record pairs the run UUID with the exact instance UUID. Before the host asks Windows to create the suspended process, it flushes and atomically publishes a no-replace `pending-run-v2` record in that instance's sample-only directory. The record carries no executable, account credential, or PID.

The protected run creates a named job object, `Local\CarbonDesktop.Sample.Job.<run UUID, no hyphens>`, with kill-on-last-close and a one-process limit. That name is the run's OS-boundary identity. A launcher that refuses an existing name never adopts or reconfigures someone else's job. On admission, a `pending-run-v2` record left by a lost owner is retired only after the launcher opens that exact name and observes either no job or a job with zero active members. A live job keeps the instance fenced. Legacy `pending-run-v1` records have no durable boundary identity and stay fenced.

If creation fails before Windows returns a process, the host can clear its own record. Once a process has been created, the record can be cleared after live job accounting reports zero active members. If admission validation rejects the suspended root, the host also waits on that exact process handle. Error paths attempt bounded termination and drain. A verified forced drain allows the record to clear but returns the original sample error instead of publishing a count.

An owner disappearing or losing the ability to observe the boundary leaves the record in place. The next launch verifies the named job before admitting anything; an unreadable job handle or a job with active members returns a recovery-required error for that instance even if the lock is free. Clearing a record requires matching the current UUID through a Windows handle validated as a regular file with one link and no reparse point. The code never signals a process by a number read from storage.

The named job does not grant another user access, but another process running as the same user can open the name and terminate the tree. That denies availability; it cannot forge drain evidence while members remain, and it cannot make the launcher adopt a foreign job. Restricting the job's security descriptor further is a separate hardening decision.

Older v1 ownership records have no instance UUID. A recognized v1 record with a free or unreadable owner lock blocks new protected samples because the old run cannot be associated with a specific instance. A live v1 owner still holds its own sample lock. Live v1 and v2 owners can coexist with unrelated new runs. Recovery preserves legacy and unrecognized records and does not remove unrelated files.

`cargo test --locked -p carbon-session` covers two real test processes contending for one instance while the other instance remains available. The child reports a distinctive status and a deliberately misspelled test filter cannot satisfy it. The tests also cover an owner exiting without running destructors, restart recovery only after the named job is absent, a live named job still fencing its instance, a refused duplicate job name, migration from a live to an unresolved v1 owner, retained transient data until verified drain, preservation of unrecognized records, and refusal to clear a mismatched or hard-linked run record.

This is a protected-sample reservation only. It provides restart recovery for a lost owner whose `pending-run-v2` record can be verified against its named job. It does not offer a force-unlock operation on legacy or unrecognized records, a production game runner, or active stop from either shell. Unknown outcomes remain fenced until an OS boundary can be verified. Player saves and installed instances remain outside this fixture storage.
