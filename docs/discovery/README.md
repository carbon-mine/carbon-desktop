Reviewed on 26 November 2026 against the saved Panel product direction and primary sources. The comparison is a desk review. The discovery worker reviewed the linked sources. ### Reproducible storage and interruption workload

The first build includes [local fixture v1](../../crates/store/src/fixtures.rs) with six deterministic inert objects and separate profile roots. Follow the [candidate walkthrough](../handoff.md) using a fresh fixture root. Generate A, create an exact repeat and a separate overlap, and review/stage B. With a healthy cache the initial local-source counters should move by 80 KiB, 0 KiB, 16 KiB and 4 KiB respectively for those four steps. Change the repeat's setting and save marker, check A's values, interrupt staging, relaunch and resume, then try corruption/repair and guarded rollback. Local source counters measure simulated payload. The optional object allocation metric measures fixture objects. The extended workload below requires controlled network and native filesystem verification.

For a controlled store-only run, generate ten distinct 10 MiB payloads. For each content label `a` through `j`, concatenate SHA-256 blocks of ASCII `carbon-store/v1/<label>/<decimal-counter>`, beginning at zero, then truncate to exactly 10 MiB. Use the same recipe for replacement labels. Fixture payloads are opaque and stay out of an executable game path. Record generated SHA-256 and exact length. Use a counting loopback fixture server or an equivalent deterministic test harness with per-digest payload counters, independently recording metadata, errors and any retries.

1. Install A with ten payloads into a disposable root. Install an exact repeat into B and verify zero duplicate payload and no more than one verified stored object per digest. Repeat with C replacing two of the ten payloads and a small-update case replacing 5 MiB of a separate 100 MiB baseline made of twenty 5 MiB payloads. Expected warm payload is 20 MiB and 5 MiB respectively with a healthy cache.
2. Measure logical length, physical allocation per install and on the whole data root before and after each step, unique objects, peak stage space and backup allocation. On Windows record volume allocation plus disk/storage tool method and hardlink IDs if used. On Linux record filesystem block allocation plus extent-sharing accounting or controlled volume deltas for reflinks. Sum unique objects or measure volume deltas to avoid counting the same blocks twice. Report private-copy fallback, cache hit rates and deduplicated disk savings separately.
3. Change B's config and save marker. Compare independent marker and blob hashes. Attempt shared writes through the native runner and verify denial. Corrupt a cache object through the host test harness, start simultaneous requests and verify a clean shared acquisition or an explicit integrity failure with no activation. After repair, release some references and verify eviction preserves remaining references and live generations.
4. Pause at verified staging and at the activation boundary using test barriers, stop the disposable process, reopen and reconcile. Repeat with a bounded scratch filesystem that cannot fit the stage and with network interruption. For each outcome verify persisted mutation journal state, complete generation contents, marker continuity and controlled retry. Test recovery while one game session owns an active generation.
5. For the plan-scale native benchmark, use the same percentages with approximately 1 GiB, add authorized real overlapping mods in two independent instances on each default filesystem, and repeat for managed A/B when authoritative fixtures arrive. With 100 profiles and two jobs, measure search and Cancel response, cold/warm startup, launcher/runner peak and idle memory, and cached Play-to-window. Record timing percentiles, package size and performance conditions. Treat initial plan budgets as calibration targets.
