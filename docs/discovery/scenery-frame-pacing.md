# Scenery frame pacing on native desktops

Use the scene's authored frame rate as its clock. Decode at most one upcoming image in the background and show the newest due image at the next available window frame. Keep presenting the current image while the next one is late. At the inspected Carbon revision, each delay starts after the previous decode completes, so decode time and foreground scheduling accumulate across frames. Reuse the existing generation check when changing scenes or leaving Home. A late callback must never restart an old scene. [Carbon at 6098e67](https://github.com/carbon-mine/carbon-desktop/blob/6098e670a77366e0b3ca1373ba192c82d1e55289/crates/gpui-launcher/src/scenery.rs)

## What GPUI schedules

GPUI 0.2.2 queues one-shot callbacks in `Window::on_next_frame`. Its platform frame handler drains the queue before deciding whether to draw or present. `request_animation_frame` registers a callback that notifies the currently rendered view. These are useful points to commit a ready image. A callback timestamp alone cannot establish when the pixels appeared on a display. Avoid registering a fresh callback at monitor rate while a static poster is visible or while an upcoming decoded frame is still far from its deadline. [Window implementation](https://docs.rs/gpui/0.2.2/src/gpui/window.rs.html#1018-1071) · [Callback APIs](https://docs.rs/gpui/0.2.2/src/gpui/window.rs.html#1640-1663)

| Platform | Driver of the update opportunity in GPUI 0.2.2 |
| --- | --- |
| Windows | A provider thread waits on DWM and signals windows. Its fallback sleeps for the estimated display interval when the wait fails or returns implausibly early. Multiple monitors can have different cadences. [Windows platform](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/platform.rs) · [DWM timing and fallback](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/vsync.rs) |
| macOS | GPUI connects a Core Video display link to a display and delivers frame requests through a main-queue dispatch source. Window operations can also initiate synchronous draws. [Display link](https://docs.rs/crate/gpui/0.2.2/source/src/platform/mac/display_link.rs) · [Window redraw](https://docs.rs/crate/gpui/0.2.2/source/src/platform/mac/window.rs) |
| Linux Wayland | GPUI requests a surface frame. The compositor's callback drives a refresh opportunity, with the next request tied to surface state. Presentation feedback is a separate protocol. [Wayland client](https://docs.rs/crate/gpui/0.2.2/source/src/platform/linux/wayland/client.rs) · [Window](https://docs.rs/crate/gpui/0.2.2/source/src/platform/linux/wayland/window.rs) · [Presentation timing protocol](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/stable/presentation-time/presentation-time.xml) |
| Linux X11 | A calloop timer uses an interval from XRandR or a 60 Hz fallback. The loop advances to a future deadline and handles hidden windows separately. Timer regularity measures scheduling, with scanout timing still a separate measurement. [X11 refresh loop](https://docs.rs/crate/gpui/0.2.2/source/src/platform/linux/x11/client.rs) |

## Decode and first paint

A new `RenderImage` has a fresh image ID and expects BGRA bytes. On image paint, GPUI asks the atlas for a tile keyed by image ID and frame index. First use can allocate and upload pixels through DirectX, Metal or Blade. Keep the current image's identity stable between authored frames and retire obsolete images after replacement. A CPU-ready image can still miss its presentation deadline on its first upload. Preloading a whole sequence trades latency for resident CPU and GPU storage. One 960 × 540 frame requires about 1.98 MiB of raw pixels before atlas overhead. [Image identity](https://docs.rs/gpui/0.2.2/src/gpui/assets.rs.html#36-79) · [Paint path](https://docs.rs/gpui/0.2.2/src/gpui/window.rs.html#3131-3175) · [DirectX](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/directx_atlas.rs) · [Metal](https://docs.rs/crate/gpui/0.2.2/source/src/platform/mac/metal_atlas.rs) · [Blade](https://docs.rs/crate/gpui/0.2.2/source/src/platform/blade/blade_atlas.rs)

The lockfile supplies `image 0.25.10`, `zune-jpeg 0.5.15` and `zune-core 0.5.3`. Zune exposes `jpeg_set_out_colorspace`, header dimensions, output-buffer size, and `decode_into` for caller-owned memory. Its YCbCr conversion dispatch selects AVX2 or NEON for RGB/RGBA where available. Direct BGRA uses its scalar conversion in this version. Before allocating output, validate the parsed dimensions and use checked arithmetic against the scene limit. [Lockfile](https://github.com/carbon-mine/carbon-desktop/blob/6098e670a77366e0b3ca1373ba192c82d1e55289/Cargo.lock) · [Decoder API](https://docs.rs/zune-jpeg/0.5.15/zune_jpeg/struct.JpegDecoder.html) · [Color conversion dispatch](https://docs.rs/crate/zune-jpeg/0.5.15/source/src/color_convert.rs)

### Native Windows x64 measurement

On an Intel Core i9-12900HK, a release build using rustc 1.99.1 decoded the first and middle JPEG from each of seven bundled sequences at 960 × 540. The probe loaded compressed frames before timing, used one warmup followed by 15 timed repetitions, and rotated the three paths for every frame and repetition. Each sample included output allocation and the indicated color conversion. It excluded disk I/O, GPUI rendering and presentation. The baseline and direct BGRA produced byte-identical buffers on all 14 inputs, with alpha 255 throughout. [Bundled inputs](https://github.com/carbon-mine/carbon-desktop/tree/6098e670a77366e0b3ca1373ba192c82d1e55289/design-system/landscapes)

| JPEG path | Samples | Median | 95th percentile |
| --- | ---: | ---: | ---: |
| Existing `image` load, convert to RGBA8, swap red/blue | 210 | 2.916 ms | 4.279 ms |
| Zune RGBA output, swap red/blue in place | 210 | 2.168 ms | 3.555 ms |
| Zune BGRA output | 210 | 2.590 ms | 3.883 ms |

Repeat with the exact pinned dependencies and `cargo run --release`. Open each `.frames` file, take frames zero and `count / 2` from its offset table, and decode them in sorted filename order. For the Zune paths use `JpegDecoder::new_with_options(ZCursor::new(bytes), DecoderOptions::default().jpeg_set_out_colorspace(mode)).decode()`. Swap channels zero and two for each RGBA pixel. Rotate path order by `(path + repetition + frame_index) % 3`. Measure allocation, decode and swizzle with `Instant`; consume the output with `black_box` after stopping the timer. Repeat on ARM64 before choosing a common default.

## Evidence for an animation change

The existing six native GitHub Actions targets can run deterministic clock tests, generation/cancellation tests, pixel checks and a release decoder probe on each CPU architecture. Save timing distributions as diagnostic output because hosted machines and their load vary. The present workflow establishes native build, unit-test and lint coverage. It does not operate a known physical monitor. Virtual display smoke tests can verify paint and state transitions if the runner exposes a compatible graphics device. [Carbon CI](https://github.com/carbon-mine/carbon-desktop/blob/6098e670a77366e0b3ca1373ba192c82d1e55289/.github/workflows/desktop-ci.yml) · [GitHub runner environments](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)

For a physical review, use the same release binary, scene, viewport and 30-second playback interval per comparison. Log the authored deadline, decode start/end, ready frame ID, draw submission, and presentation timestamp where available. Report missed authored deadlines, repeated/skipped frames, p50/p95/p99 between visible changes and peak retained frame bytes. Capture the cold first paint separately from steady playback. Compare at 60 Hz and a higher refresh rate, record the GPU, display, scaling and power mode, then repeat after resizing or moving the window. Verify scenery decoding and animation-triggered wakeups stop on Library, reduced motion, and a hidden or minimized Home. Application focus loss alone does not prove occlusion. Measure the launcher separately from any active game. [Windows PresentMon](https://github.com/GameTechDev/PresentMon) · [Metal presented time](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime) · [Wayland presentation feedback](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/stable/presentation-time/presentation-time.xml)

Physical presentation measurements on Windows, macOS and native Linux remain open. The Windows numbers above measure decoder work. A WSLg run can exercise a virtualized GUI pipeline and should be recorded separately from native Linux display measurements.
