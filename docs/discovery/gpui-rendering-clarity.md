# GPUI rendering clarity

Compare the GPUI launcher with the Svelte/Tauri launcher on the same display. The initial source review on 26 November 2026 uses the Windows and Linux implementations shipped in GPUI 0.2.2 and gpui-component 0.5.1. The recommendations below are experiments. This review does not establish visual parity or identify the cause on the owner's machine. [Dependency lock](../../Cargo.lock)

## First differences to test

| Surface | Source finding | First experiment |
| --- | --- | --- |
| Windows text | The web theme requests Segoe UI Variable, then Segoe UI. The GPUI theme and main view explicitly request Segoe UI. Microsoft documents weight and optical sizing for the variable face. HTML can use automatic optical sizing. The equivalent behavior in Carbon's pinned native renderer needs measurement. | Use the rendered-font inspector on the Svelte reference to record the actual face, including which family the fallback selected. Resolve the available native face once for both the GPUI root and component theme. Compare static and variable text faces before adopting one. |
| Linux text | Web uses CSS system-ui. GPUI's Linux backend translates the .SystemUIFont alias to IBM Plex Sans and has additional font fallback behavior. Those paths can resolve to different installed faces. GPUI uses cosmic-text and SwashCache. | On native Linux record the desktop UI font, web rendered font, installed GPUI font names and actual selected face. Compare the same regular and semibold faces first. |
| Text metrics | Web body text uses 0.875rem and line height 1.45. GPUI sets 14 logical pixels at its root and uses explicit sizes and rem-based role styles in different places. The component root sets the window rem from the theme. The web button rule uses weight 500 and GPUI Play requests semibold. A shared body size does not ensure the same caption, baseline or title. | Measure title, body, library subtitle, settings label/value and Play caption independently. Give each role a matching logical size, weight, line height and contrast. Check dialogs and menus too. |
| Control artwork | The GPUI SVG paint path sizes its raster using the window scale and a 2× smoothing factor, then rounds the sprite origin in device coordinates. The repository has a shared native SVG control set. | Render the actual SVG directly at the target size. Compare stroke weight, negative space and alignment at the physical pixel size of a toolbar icon. Test pixel-art instance imagery separately with integer source-grid multiples where practical. |

## Windows renderer boundary

The pinned DirectWrite implementation requests grayscale antialiasing when it creates glyph-run analysis. The DirectX renderer obtains gamma and grayscale-enhanced contrast from Windows rendering parameters, and the monochrome glyph shader applies correction. GPUI reads the window DPI to compute its scale. Check the executable's actual DPI awareness, the GPUI window scale and the number of device pixels per logical pixel on each monitor. If the compositor stretches the whole window, both text and thin geometry can soften. This is a diagnostic hypothesis until captured. [DirectWrite](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/direct_write.rs), [DirectX parameters](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/directx_renderer.rs), [glyph shader](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/shaders.hlsl), [window DPI](https://docs.rs/crate/gpui/0.2.2/source/src/platform/windows/window.rs).

## Paired review

1. Use identical fixture data, window size in logical pixels, light or dark theme, display, OS text settings and default webview zoom. Capture both windows as lossless PNGs at their original device resolution. Record frontend revisions, monitor scale, observed font faces and rendered dimensions. Keep captures containing personal data out of source control.
2. Start on Windows at 100%, 125% and 150%, including a move between differently scaled monitors where available. Repeat on native Linux at a supported integral and fractional scale. Record whether the launcher used Wayland or X11. Reserve native Linux acceptance for a native session.
3. Compare the library, Settings and Play control using the same text. Include small numerals, punctuation, long names and a fallback-script sample. Inspect original-size crops side by side. Look for crowded baselines, disappearing counters, uneven icon strokes, fuzzy dividers and inconsistent disabled text. Check light and dark themes, keyboard focus and OS high contrast.
4. Change one variable per pass. Verify the DPI path first, actual font family second, then per-role metrics and icon geometry. Review screenshots at 1:1 on the target monitor with the owner. Record which variant reads as clearly as the web reference at each size. Bounding boxes and pixel differences help locate issues, while reader judgment determines legibility.
5. If matched metrics and native resolution still leave a repeatable glyph-quality gap, isolate it in a small GPUI text specimen. Compare one newer compatible renderer on an experimental branch. Record quality, idle memory, scrolling frame times and accessibility regressions before proposing a dependency change. Treat grayscale/subpixel behavior as renderer-specific and preserve platform accessibility preferences.
